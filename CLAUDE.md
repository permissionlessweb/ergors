## Team Organization Structure

- **ALL team-shared resources (agents, skills, MCP servers, tools, plans) live in `.team/` folder as single source of truth**. `.opencode/` and `.claude/` folders contain symlinks to `.team/` subdirectories for CLI/TUI compatibility. Never duplicate content—always reference `.team/` directly.

## Project Principles

- We are building tools that respect not only users time, but our soveregnty, and privacy. Maintain this in mind when building our features, as these principles avoid unnesseary complexity. This means we prioritize minimizeing type bloat/ tech-debt causing implementations. We build off of Test-driven-development, with integrity of design tests that do not give a false sense of security. This will allow us to strenthen the inter-collaborative trust between ourselves, and our code.
- `docs/spec.md` is the informational manifold for awaress of the location of logic for this workspace.
- ALL cli references are located in `./packages/ergors/CLI_REFERENCE.md`. ALWAYS when new cli features or iterating features, we update these to maintain accurate.
- ALWAYS use `cargo chec` & `cargo tes` in replacement of `cargo check`. this will decrease the overall character count of errors and warning without stripping the core issues. Outputs a JSON array like ["Error (severity 5)...", "Related..."]. No errors? [].
- always use our justfile commands to invoke workflow actions such as building libraries.
- NEVER modify prost generated types manually in `./packages/ho-std/src/types/ergors/gen`.
- ALWAYS regenerate using `cargo run` in proto directory.
- This is a rust-project using our types & clients generated by proto3 definitions in proto for interoperable reproducible libraries.
- USE ONLY EXISTING TYPES DEFINED IN PACKAGE. ALWAYS GENERATE NEW TYPES WITH PROTO3 DEFINITIONS FOR GENERATIVE VERSIONING CONTROL.

- ALWAYS take the opportunity to minimize new type difintions, for preventing unesseary type bloat & tech-debt.
- ALL types generated from types give us access to the prost::name & type_url(). prioritize use of these over hard coded type urls when interacting with msgs.
- when performing code reviews, write the review to a md file to share with teammates. keep these organized in a dedicated `review` folder, with subfolders of the primary task at hand (not the current task being done, but the singular high level task that the multiple incremental steps we take (implement review, review-review) is specific to. ). for example, if we are integrating discord gateway support, we have one subfolder in the review folder that is dedicated to all the turns/steps for reviewing in `review/discord-gateway/**`
